# Android Posts App --- Complete Coding Assessment Notes

**Stack:** Kotlin · Jetpack Compose · Retrofit · Hilt · Coroutines ·
StateFlow · MVVM · Clean Architecture · JUnit · MockK

**API:** `https://jsonplaceholder.typicode.com/posts`

**Goal:** Build a working Posts app that fetches posts, displays
title/body in a scrollable list, handles loading/error/empty states,
supports retry, and has unit tests for Repository, UseCase, and
ViewModel.

------------------------------------------------------------------------

## 1. What the app should do

### Functional requirements

1.  Fetch posts from `GET /posts`.
2.  Display each post's title and body in a Compose `LazyColumn`.
3.  Show a loading indicator while the request is running.
4.  Show an error message and Retry button if the request fails.
5.  Show an empty state if the API returns an empty list.
6.  Convert API DTOs into domain models.
7.  Use Hilt to provide Retrofit, API, and Repository dependencies.
8.  Test the Repository, UseCase, and ViewModel without making real
    network calls.

### API details

-   Base URL: `https://jsonplaceholder.typicode.com/`
-   Endpoint: `posts` --- **plural**
-   Full URL: `https://jsonplaceholder.typicode.com/posts`
-   Expected response: JSON array containing objects with `userId`,
    `id`, `title`, and `body`.

Example response item:

``` json
{
  "userId": 1,
  "id": 1,
  "title": "sunt aut facere",
  "body": "quia et suscipit..."
}
```

**Common mistake:** `@GET("post")` calls the wrong endpoint and returns
HTTP 404. Use `@GET("posts")`.

## 2. Architecture and request flow

``` text
Compose PostsScreen
       |
       | observes StateFlow
       v
PostsViewModel
       |
       | calls
       v
GetPostsUseCase
       |
       | depends on abstraction
       v
PostsRepository (domain interface)
       ^
       | implemented by
       |
PostsRepositoryImpl (data)
       |
       v
PostsApi (Retrofit)
       |
       v
GET /posts
```

### Layer responsibilities

  -----------------------------------------------------------------------
  Layer                   Responsibility          Main classes
  ----------------------- ----------------------- -----------------------
  Presentation            UI, user interaction,   `PostsScreen`,
                          UI state                `PostsViewModel`,
                                                  `PostsUiState`

  Domain                  Business model and      `Post`,
                          business operation      `PostsRepository`,
                                                  `GetPostsUseCase`

  Data                    API communication and   `PostsApi`, `PostDto`,
                          mapping                 `PostMapper`,
                                                  `PostsRepositoryImpl`

  DI                      Dependency creation and `NetworkModule`,
                          wiring                  `PostsApplication`
  -----------------------------------------------------------------------

### Dependency rule

-   Presentation depends on Domain.
-   Data depends on Domain abstractions/models.
-   Domain should not depend on Android, Retrofit, Gson, or Compose.
-   Hilt wires the concrete implementations together.

### Why DTO and domain model are separate

-   `PostDto` represents the external API contract.
-   `Post` represents the data the app needs.
-   API changes should not unnecessarily leak into business logic or UI.
-   Mapping is explicit and easy to test.

## 4. Gradle setup

### Important version guidance

Android Studio templates differ. Keep the Kotlin, Android Gradle Plugin
(AGP), Compose compiler, KSP/KAPT, and Gradle versions generated by your
project. Do not copy a plugin version blindly.

For this implementation, use **KAPT for Hilt** to avoid mixing Hilt's
KSP and KAPT compiler configurations. If your project already uses KSP
for other processors, that is fine; use only one processor for Hilt.

### Option A --- Direct dependencies

In the app module `build.gradle.kts`, add the Hilt plugin and KAPT
plugin using versions compatible with the project:

``` kotlin
plugins {
    // Keep the Android and Kotlin/Compose plugins generated by Android Studio.
    id("com.google.dagger.hilt.android")
    id("org.jetbrains.kotlin.kapt")
}
```

If plugin versions are declared in the root build file, declare them
there with `apply false`. The KAPT plugin version must match the Kotlin
plugin version.

Add dependencies:

``` kotlin
dependencies {
    // Retrofit
```

### 6.6 `data/repository/PostsRepositoryImpl.kt`

``` kotlin
package com.example.postsapp.data.repository

import com.example.postsapp.data.mapper.toDomain
import com.example.postsapp.data.remote.PostsApi
import com.example.postsapp.domain.model.Post
import com.example.postsapp.domain.repository.PostsRepository
import javax.inject.Inject

class PostsRepositoryImpl @Inject constructor(
    private val api: PostsApi
) : PostsRepository {

    override suspend fun getPosts(): List<Post> {
        return api.getPosts().map { it.toDomain() }
    }
}
```

**What happens here?**

1.  Repository calls Retrofit API.
2.  API returns `List<PostDto>`.
3.  `map` converts each DTO to `Post`.
4.  Repository returns `List<Post>` to the domain layer.

### 8.2 `di/NetworkModule.kt`

``` kotlin
package com.example.postsapp.di

import com.example.postsapp.data.remote.PostsApi
import com.example.postsapp.data.repository.PostsRepositoryImpl
import com.example.postsapp.domain.repository.PostsRepository
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import okhttp3.OkHttpClient
import okhttp3.logging.HttpLoggingInterceptor
import retrofit2.Retrofit
import retrofit2.converter.gson.GsonConverterFactory
import javax.inject.Singleton

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {

    @Provides
    @Singleton
    fun provideLoggingInterceptor(): HttpLoggingInterceptor {
        return HttpLoggingInterceptor().apply {
            level = HttpLoggingInterceptor.Level.BASIC
        }
    }

    @Provides
    @Singleton
    fun provideOkHttpClient(
        logging: HttpLoggingInterceptor
    ): OkHttpClient {
        return OkHttpClient.Builder()
            .addInterceptor(logging)
            .build()
    }

    @Provides
    @Singleton
    fun provideRetrofit(
        client: OkHttpClient
    ): Retrofit {
        return Retrofit.Builder()
            .baseUrl(PostsApi.BASE_URL)
            .client(client)
            .addConverterFactory(GsonConverterFactory.create())
            .build()
    }

    @Provides
    @Singleton
    fun providePostsApi(retrofit: Retrofit): PostsApi {
        return retrofit.create(PostsApi::class.java)
    }

    @Provides
    @Singleton
    fun providePostsRepository(
        implementation: PostsRepositoryImpl
    ): PostsRepository = implementation
}
```

**Why Singleton?** Retrofit, OkHttpClient, API service, and repository
can be reused rather than recreated for every request.

**Logging note:** BASIC logging is less noisy. BODY logging is useful
while debugging but avoid logging sensitive production payloads.

### 9.1 `presentation/PostsUiState.kt`

This single immutable state represents loading, success, empty, and

### 9.2 `presentation/PostsViewModel.kt`

``` kotlin
package com.example.postsapp.presentation

import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope
import com.example.postsapp.domain.usecase.GetPostsUseCase
import dagger.hilt.android.lifecycle.HiltViewModel
import javax.inject.Inject
import kotlinx.coroutines.CancellationException
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.update
import kotlinx.coroutines.launch

@HiltViewModel
class PostsViewModel @Inject constructor(
    private val getPostsUseCase: GetPostsUseCase
) : ViewModel() {

    private val _uiState = MutableStateFlow(PostsUiState())
    val uiState = _uiState.asStateFlow()

    init {
        fetchPosts()
    }

    fun fetchPosts() {
        viewModelScope.launch {
            _uiState.update {
                it.copy(isLoading = true, error = null)
            }

            try {
                val posts = getPostsUseCase()

                _uiState.update {
                    it.copy(
                        isLoading = false,
                        posts = posts,
                        error = null
                    )
                }
            } catch (e: CancellationException) {
                throw e
            } catch (e: Exception) {
                _uiState.update {
                    it.copy(
                        isLoading = false,
                        error = e.message ?: "Something went wrong"
                    )
                }
            }
        }
    }
}
```

**Why rethrow CancellationException?** Coroutine cancellation is a
control signal, not an ordinary application failure. It should not be
converted into an error state.

``` kotlin
            TopAppBar(title = { Text("Posts Directory") })

                .padding(16.dp)

                        CircularProgressIndicator()
                        Spacer(Modifier.height(12.dp))

                        modifier = Modifier.fillMaxSize(),

                            Text("Retry")
                        }
                    }
                }

                state.posts.isEmpty() -> {
                    Text("No posts available")
                }

                else -> {
                    LazyColumn(
                        verticalArrangement = Arrangement.spacedBy(12.dp)
                    ) {
                        items(
                            items = state.posts,
                            key = { post -> post.id }
                        ) { post ->
                            Card(
                                modifier = Modifier.fillMaxWidth()
                            ) {
                                Column(Modifier.padding(16.dp)) {
                                    Text(
                                        text = post.title,
                                        style = MaterialTheme.typography.titleMedium
                                    )
                                    Spacer(Modifier.height(8.dp))
                                    Text(
                                        text = post.body,
                                        style = MaterialTheme.typography.bodyMedium
                                    )
                                }
                            }
                        }
                    }
                }
            }
        }
    }
}
```

## 10. Unit testing strategy

Use the Arrange--Act--Assert pattern:

1.  **Arrange:** Prepare test data and mock dependencies.
2.  **Act:** Call the method being tested.
3.  **Assert:** Verify the result and interactions.

Never make a real HTTP call in these unit tests. Mock the API for
Repository tests, Repository for UseCase tests, and UseCase for
ViewModel tests.

### Test matrix

  Layer        Test                            Expected result
  ------------ ------------------------------- --------------------------------------
  Repository   API returns DTO list            Correct domain list returned
  Repository   API returns empty list          Empty list returned
  Repository   API throws exception            Exception propagated
  UseCase      Repository returns posts        Posts returned
  UseCase      Repository returns empty list   Empty list returned
  ViewModel    UseCase succeeds                Posts set, loading false, error null
  ViewModel    UseCase fails                   Error set, loading false
  ViewModel    Retry after failure             Second call succeeds
  ViewModel    Empty response                  Empty list, no error, loading false

## 11. Test dispatcher rule

### `presentation/MainDispatcherRule.kt`

``` kotlin
package com.example.postsapp.presentation

import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.ExperimentalCoroutinesApi
import kotlinx.coroutines.test.StandardTestDispatcher
import kotlinx.coroutines.test.TestDispatcher
import kotlinx.coroutines.test.resetMain
import kotlinx.coroutines.test.setMain
import org.junit.rules.TestWatcher
import org.junit.runner.Description

@OptIn(ExperimentalCoroutinesApi::class)
class MainDispatcherRule(
    val dispatcher: TestDispatcher = StandardTestDispatcher()
) : TestWatcher() {

    override fun starting(description: Description) {
        Dispatchers.setMain(dispatcher)
    }

    override fun finished(description: Description) {
        Dispatchers.resetMain()
    }
}
```

`StandardTestDispatcher` queues coroutine work until the test scheduler
advances. This makes asynchronous ViewModel work deterministic.

## 12. Repository unit tests

### `data/repository/PostsRepositoryImplTest.kt`

``` kotlin
package com.example.postsapp.data.repository

import com.example.postsapp.data.remote.PostDto
import com.example.postsapp.data.remote.PostsApi
import com.example.postsapp.domain.model.Post
import io.mockk.coEvery
import io.mockk.coVerify
import io.mockk.mockk
import kotlinx.coroutines.test.runTest
import org.junit.Assert.assertEquals
import org.junit.Assert.assertTrue
import org.junit.Test

class PostsRepositoryImplTest {

    private val api: PostsApi = mockk()
    private val repository = PostsRepositoryImpl(api)

    @Test
    fun `getPosts returns mapped domain models`() = runTest {
        // Arrange
        val dtoList = listOf(
            PostDto(
                userId = 1,
                id = 1,
                title = "Test title",
                body = "Test body"
            )
        )
        val expected = listOf(
            Post(
                id = 1,
                title = "Test title",
                body = "Test body"
            )
        )
        coEvery { api.getPosts() } returns dtoList

        // Act
        val result = repository.getPosts()

        // Assert
        assertEquals(expected, result)
        coVerify(exactly = 1) { api.getPosts() }
    }

    @Test
    fun `getPosts returns empty list`() = runTest {
        // Arrange
        coEvery { api.getPosts() } returns emptyList()

        // Act
        val result = repository.getPosts()

        // Assert
        assertTrue(result.isEmpty())
    }

    @Test
    fun `getPosts propagates api exception`() = runTest {
        // Arrange
        coEvery { api.getPosts() } throws RuntimeException("Network error")

        // Act
        val exception = try {
            repository.getPosts()
            null
        } catch (e: RuntimeException) {
            e
        }

        // Assert
        assertEquals("Network error", exception?.message)
    }
}
```

What this verifies:

-   DTO-to-domain mapping is correct.
-   Empty API responses are handled.
-   Repository does not silently swallow API exceptions.

``` kotlin
import org.junit.Assert.assertNull
import org.junit.Assert.assertTrue
import org.junit.Rule
import org.junit.Test

@OptIn(ExperimentalCoroutinesApi::class)
class PostsViewModelTest {

    @get:Rule
    val mainDispatcherRule = MainDispatcherRule()

    private val useCase: GetPostsUseCase = mockk()

    private val posts = listOf(
        Post(
            id = 1,
            title = "Test title",
            body = "Test body"
        )
    )

    @Test
    fun `fetchPosts success updates ui state`() =
        runTest(mainDispatcherRule.dispatcher) {
            // Arrange
            coEvery { useCase() } returns posts

            // Act
            val viewModel = PostsViewModel(useCase)
            advanceUntilIdle()

            // Assert
            val state = viewModel.uiState.value
            assertEquals(posts, state.posts)
            assertFalse(state.isLoading)
            assertNull(state.error)
        }

    @Test
    fun `fetchPosts failure updates error state`() =
        runTest(mainDispatcherRule.dispatcher) {
            // Arrange
            coEvery { useCase() } throws RuntimeException("Network error")

            // Act
            val viewModel = PostsViewModel(useCase)
            advanceUntilIdle()

            // Assert
            val state = viewModel.uiState.value
            assertEquals("Network error", state.error)
            assertFalse(state.isLoading)
            assertTrue(state.posts.isEmpty())
        }

    @Test
    fun `retry after failure loads posts successfully`() =
        runTest(mainDispatcherRule.dispatcher) {
            // Arrange
            var callCount = 0
            coEvery { useCase() } coAnswers {
                callCount++
                if (callCount == 1) {
                    throw RuntimeException("Network error")
                } else {
                    posts
                }
            }

            // Act
            val viewModel = PostsViewModel(useCase)
            advanceUntilIdle()

            // First request failed
            assertEquals("Network error", viewModel.uiState.value.error)

            // Retry
            viewModel.fetchPosts()
            advanceUntilIdle()

            // Assert
            val state = viewModel.uiState.value
            assertEquals(posts, state.posts)
            assertNull(state.error)
            assertFalse(state.isLoading)
            coVerify(exactly = 2) { useCase() }
        }

    @Test
    fun `fetchPosts empty response updates ui state`() =
        runTest(mainDispatcherRule.dispatcher) {
            // Arrange
            coEvery { useCase() } returns emptyList()

            // Act
            val viewModel = PostsViewModel(useCase)
            advanceUntilIdle()

            // Assert
            val state = viewModel.uiState.value
            assertTrue(state.posts.isEmpty())
            assertFalse(state.isLoading)
            assertNull(state.error)
        }
}
```

### Why does the ViewModel test use `advanceUntilIdle()`?

The ViewModel starts its request inside `viewModelScope.launch`. The
test dispatcher controls that coroutine. `advanceUntilIdle()` runs
scheduled work until no tasks remain, so assertions happen after the
request completes.

### KSP versus KAPT

Do not configure both KSP and KAPT to process the same Hilt compiler. If
the KSP error occurs, inspect the full stack trace to identify the
processor and verify Kotlin/KSP compatibility. Switching Hilt to KAPT
can be a practical workaround, but it is not a guaranteed fix for every
processor error.

### Short architecture explanation

"The Compose screen observes the ViewModel's StateFlow. The ViewModel
calls GetPostsUseCase, which depends on the PostsRepository interface.
The data-layer implementation calls the Retrofit API, receives PostDto
objects, maps them to domain Post models, and returns them. The
ViewModel updates UI state, and Compose recomposes. Hilt provides the
concrete dependencies. I test each layer independently by mocking its
direct dependency."
